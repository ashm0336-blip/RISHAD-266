# RISHAD 266 — خطة مجال التنبيهات والتعاميم

التاريخ: 29 أكتوبر 2026.

**الحالة: خطة مقترحة، وليست تنفيذًا أو نتيجة اختبار.** لم تُضف هذه الوثيقة API أو جداول أو ترحيلات. يبدأ تنفيذها بعد اعتماد نتائج المجموعة الحالية واكتمال إعادة تهيئة Preview والتحقق من عزلها. لا تفترض الخطة تطابق بيانات Preview مع Production.

## القرار والنطاق

المجال التالي المقترح بعد الإحصائيات اليومية هو التنبيهات والتعاميم. تُنقل بياناته إلى جداول D1 مباشرة، وتُزال كتاباته وقراءاته القديمة من المصدر. لا تُنشأ واجهة تخفي مخزن JSON القديم ولا تُحفظ نسختان دائمتان من البيانات.

يشمل الانتقال أربعة موارد:

| المورد الحالي | المسؤولية |
| --- | --- |
| `bsdept:<department>:bassam_notif_v1` | رسائل الإدارة، حالات المستخدمين، ومنع تكرار الأحداث |
| `bassam_notif_sys_v1` | رسائل مدير المنصة وحالاته |
| `bassam_bc_v1` | التعاميم العامة واستهدافها وجدولتها وسحبها |
| `bassam_notif_cfg_v1` | فروق إعدادات أنواع التنبيهات عن الإعدادات الافتراضية |

يبقى `bassam_notif_mute_v1` تفضيل جهاز. تُراجع علامة `bassam_notif_dev_v1:<uid>` باعتبارها علامة شخصية مستقلة؛ لا تُنقل ضمنيًا إلى سجل الرسائل ولا تتوسع صلاحية كتابتها.

اختير المجال قبل `daily` و`dreport` لأن الجولات ترتبط بهندسة المواقع والصور والخطة، والتقارير ترتبط بسحب الجداول والحضور والقيادة والأقفال. هذه مقارنة من قراءة المصدر، وليست تقديرًا زمنيًا أو ضمانًا بأن التنفيذ صغير.

## النموذج العلائقي المقترح

الأسماء التالية تصميم مقترح، وليست أسماء جداول مطبقة. يُثبت مخطط الحقول النهائي بمقارنة فعلية لكل حقول الرسائل والتعاميم الحالية قبل كتابة الترحيل.

| الجدول المقترح | البيانات والقيود الأساسية |
| --- | --- |
| `notification_messages` | معرف الرسالة ونطاقها، إدارة الحدث، النوع والتصنيف والأولوية والقناة، العنوان والنص، الكاتب، الموعد والانتهاء والسحب، الرابط، وأعلام التأكيد والتثبيت والمعاينة. أعمدة صريحة؛ لا عمود لوثيقة الرسالة كاملة |
| `notification_targets` | صفوف الاستهداف المرتبطة بالرسالة، بنوع محدد مثل موظف أو دور أو إدارة أو وردية. تحفظ دلالة الاستهداف الحالية دون اختزالها إلى قائمة حسابات وقت الإرسال |
| `notification_user_state` | القراءة والتأكيد والإخفاء لكل حساب ورسالة. تُشتق هوية صاحب الحالة من الجلسة، ولا يقبل الخادم هوية بديلة من الجسم |
| `notification_dedup` | مفتاح `once` وتوقيته داخل نطاقه، بقيد فريد يمنع التكرار بين المتصفحات والطلبات المتزامنة |
| `notification_type_overrides` | فروق الإعدادات فقط: التفعيل، الأولوية، القناة، النص، وأهداف `own/lead/mgr/sys` كأعلام صريحة، مع الحفاظ على معنى غياب القيمة واستعمال الافتراضي |
| مراجعات النطاق | مراجعة مستقلة للعمليات القابلة للتعديل وعمليات الاستيراد. يمكن إعادة استعمال آلية المراجعات الحالية دون إعادة تخزين المستند في KV |

تُحدد المفاتيح المركبة بحيث لا يختلط نطاق المنصة بنطاق الإدارة، ولا يُفترض تفرد معرفات الرسائل القديمة عالميًا. تُحل مفاتيح المستخدم القديمة مثل `ekey` ومعرف الحساب أثناء الاستيراد وفق الهوية الحالية؛ التعارض أو الغموض يُبلّغ عنه ولا يُنسب بصمت إلى حساب آخر. لا تُغيّر معرفات الحسابات لمعالجة هذا التحويل.

يظل استهداف الأدوار والقيادة والورديات والتعاميم مطابقًا للسياسة الحالية. لا تتحول قيمة العدد المحفوظة في تعميم قديم إلى دليل صلاحية أو إلى قائمة مستلمين نهائية.

## عقد API المقترح

- قراءة محدودة بالجلسة والنطاق عبر `GET /api/notifications`، مع ترقيم نتائج ومراجعة أو مؤشر تغير. ينفذ الخادم حكم الجمهور والصلاحيات؛ لا يعتمد على إخفاء الرسائل في الواجهة وحده.
- عمليات محددة لإطلاق حدث، وتحديث حالة المستخدم، وإرسال التعميم أو سحبه وتذكير غير القارئين، وتعديل إعدادات النوع. تُثبت المسارات والأجسام في العقود قبل التنفيذ.
- يختار الخادم الكاتب وصاحب حالة القراءة، ويتحقق من الإدارة والسقف والوحدة وأوراق الصلاحية الحالية. يرفض الحقول غير المعروفة، وتزوير الهوية، والجسم الفارغ، والأحجام الزائدة.
- يستخدم إدراج الأحداث مفتاح منع تكرار؛ تستخدم تعديلات الإعدادات والتعاميم والاستيراد مراجعة متوقعة حيث يلزم. لا يعيد تحديث قراءة رسالة كتابة قائمة الرسائل كلها.
- تؤكد الواجهة نجاح العملية بعد ACK صحيح. عند انقطاع الشبكة أو الرفض يبقى التعديل معلقًا أو يظهر الخطأ؛ لا يتحول التخزين المحلي إلى مرجع لأعمال المنصة.
- بعد الانتقال، يُرفض أي طلب حفظ قديم يضم المفاتيح المتقاعدة قبل كتابة أي جزء منه، وتُزال نسخها من الإقلاع والمزامنة.

## الحسابات والصلاحيات والتوافق

لا تشمل هذه الخطوة تعديل المصادقة أو كلمات المرور أو بصماتها أو الأدوار أو قواعد منح الصلاحيات. تستعمل API الجلسة والمفوض الحاليين، وتحافظ على نظام حسابات الموظفين ومدير المنصة. لا حساب افتراضي ولا بذرة بيانات اعتماد ولا مسار تأسيس عام.

تُثبت اختبارات المقارنة سلوك مدير المنصة ومدير الإدارة والموظف والقيادة والمكلف مباشرة، بما يشمل حدود الإدارات والقراءة والتأكيد والإخفاء والتعميم. إذا كشف الفحص فرقًا بين سياسة الصلاحية المعتمدة وسلوك قديم متساهل، يوثق الفرق ويعالج صراحة؛ لا يُنسخ التجاوز باعتباره توافقًا مطلوبًا.

يُحافظ على فرز الرسائل وتثبيت غير المقروء منها، وعلى الجدولة والانتهاء والسحب والتذكير، وعلى سلوك القراءة والتأكيد والإخفاء الفردي والجماعي. يحتاج التشذيب الحالي إلى اختبار دقيق: 400 رسالة و90 يومًا، مع مراعاة أن حالة مدير المنصة قد تشير إلى رسائل إدارات لا توجد داخل مخزنه الشخصي.

## الاستيراد والتصدير وإزالة القديم

1. إضافة `domains.notifications` بعقد إصدار واضح إلى النسخة الاحتياطية، شاملاً الرسائل والاستهداف والحالات ومنع التكرار والإعدادات اللازمة لاستعادة السلوك.
2. تحويل الموارد القديمة مرة واحدة عبر مستورد صريح يتحقق من الهوية والنطاق والتكرار والترابط قبل الكتابة. لا fallback صامت إلى قراءة KV عند فقد صف SQL.
3. تصميم الاستعادة كعملية ذرية تشمل مجال التنبيهات وما يرافقها من مجالات. لا يُعلن نجاح نسخة كاملة بعد استعادة جزء منها، ولا يبدأ أي تعديل إذا كان شكل النسخة غير مدعوم.
4. تحديث منتج المهام والمراقب والواجهة والإدارة والمزامنة معًا، ثم رفض الحفظ القديم وإزالة شيفرته وموارده المتقاعدة.
5. إثبات عدم بقاء قراءة أو كتابة أعمال إلى المفاتيح الأربعة؛ يجوز ذكر أسمائها في مستورد التوافق واختبارات المنع والتوثيق فقط.

البدء بجدول جديد مع استمرار الكتابة إلى مخزن التنبيهات القديم لا يحقق هذه الخطة.

## الاختبارات المطلوبة قبل الاعتماد

- **الهوية والصلاحيات:** جلسة مفقودة أو منتهية، موظف مقابل مدير، حدود الإدارات والفروع، حصرية SYS، تزوير الكاتب، وتعديل قراءة أو تأكيد أو إخفاء حساب آخر. لا تغيير في اختبارات الحسابات وسياسة كلمات المرور الحالية.
- **التزامن:** متصفحان يقرآن أو يؤكدان أثناء إضافة رسائل، عدم فقد الأحداث، تنافس مفاتيح `once`، ومراجعة إعدادات أو تعميم قديمة. فشل أي جزء من دفعة الاستيراد لا يترك صفوفًا جزئية.
- **السلوك:** الفرز والتثبيت، حالات الفرد والجماعة، التعاميم الملزمة، الجدولة والانتهاء والسحب والتذكير، والاستهداف المتغير حسب الموظف والدور والقيادة والوردية.
- **الاحتفاظ:** حدود العمر والعدد، وتنظيف منع التكرار والحالات دون حذف حالات لازمة لرسائل إدارة أخرى عند مدير المنصة.
- **منتج المهام:** إدراج SQL مباشر، عدم تكرار الحدث، واحترام إعدادات نوع التنبيه. يبقى فشل التنبيه بعد نجاح المهمة ظاهرًا في الرصد دون الادعاء بفشل المهمة أو ذريتها معه.
- **الواجهة والشبكة:** ACK ناقص أو قديم، أخطاء الصلاحية والتعارض، انقطاع الشبكة وتبدل المستخدم. لا رسالة نجاح متفائلة ولا أعمال محفوظة محليًا باعتبارها مرجعًا.
- **الترحيل والنسخ الاحتياطية:** بيانات تركيبية تغطي كل الحقول والمفاتيح المركبة، تطابق التصدير والاستعادة، رفض حساب ملتبس، رفض نسخة غير مدعومة قبل أي كتابة، والتأكد من عدم ظهور أسرار ضمن التصدير العادي.
- **إزالة المسار القديم:** فحص المصدر والاختبارات يثبت منع المفاتيح المتقاعدة في الحفظ والإقلاع، وعدم وجود dual write أو نسخة KV دائمة.
- **التكامل:** اختبارات العقود وتوليد مخططات الأجسام والعامل، المجموعة الحالية كاملة، البناء الحتمي، وحدود الحجم والأداء، ثم اختبارات Preview المعزولة مع فحص الموارد الفعلية.

هذه قائمة قبول مستقبلية. لا تعني أن أيًا من اختبارات هذا المجال الجديد قد شُغّل أو نجح.

## حدود التنفيذ

التنفيذ السحابي، إن بدأ، يقتصر على قاعدة Preview المعتمدة وبعد التحقق من هويتها وارتباطاتها الفعلية. لا تتضمن الخطة تعديل `bassam-db` أو حذف حاويات R2 أو نشر Production أو Commit أو Push. لا تُنسخ بيانات أو بصمات حسابات إلى ملفات المصدر أو fixtures؛ تستخدم الاختبارات بيانات تركيبية، ويظل أي تصدير خاص خارج Git.
