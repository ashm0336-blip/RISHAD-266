# خطة الاستعادة الشاملة الذرية

الحالة الحالية — 30 أكتوبر2026: نُفذ مترجم الاستعادة المختلطة في `workers/parts/019d-atomic-restore.js` والأجزاء019e/019f، واختُبر في المصدر7 محليًا. لم يُرحّل إلىPreview بعد؛ المخطط السحابي5 وبوابة عزل النسخ القديمة في[Playbook](RISHAD266_PLAYBOOK.md) ما زالت قائمة. ما يلي خطة تاريخية قبل التنفيذ، بما فيها جسم الطلب المقترح؛ عقدAPI الحالي في `src/api/contracts.json` والمصدر، ولا تُعتمد الحقول المقترحة أدناه للتشغيل.

## النطاق والقرار

الهدف استعادة بيانات KV والإحصائيات العلائقية والمراجعات والتدقيق وإبطال الجلسات المرتبط بتغييرات الحسابات داخل معاملة D1 واحدة. لا حفظ متفائل في المتصفح، ولا سلسلة طلبات تحفظ المجالات تباعًا، ولا كتابة مزدوجة لبيانات الإحصائيات في KV والجداول الجديدة.

الحل المقترح يستخدم تقييم `applySave` وحراسه الحاليين، ثم يحوّل النتائج المعتمدة إلى صفوف SQL مجمعة. لن يُستدعى `applySave` الحالي ثم `dsDomainCommit` تباعًا؛ فهذا يثبت المجال الأول قبل التأكد من الثاني.

حد 90 عبارة مع الرفض الكامل آمن للفشل، لكنه لا يغلق الوظيفة للحجم المعروف: جرد Preview السابق احتوى 154 مفتاحًا منطقيًا و159 صف KV و13,006 حسابات. توليد عدة عبارات لكل مفتاح سيجاوز ذلك الحد. يلزم تجميع الصفوف، ثم قياس عدد العبارات والبايتات على نسخة محلية من البيانات المصرح بها؛ ولا يجوز افتراض أن Preview تمثل Production.

## ما تحقق من التنفيذ القائم

- يقيّم `workers/parts/054-image-contract.js` المفاتيح أولًا، ويمر عبر `canWrite` أو `canWriteEnf` وسياسات الاستعادة ودمج الحقول المحجوبة وثوابت الهوية.
- ينفذ `applySave` الحالي تخصيص المراجعة عبر `nextRev` خارج دفعة بيانات المفاتيح. ويكتب عبارات اللقطات والسجلات قبل استدعاء `commitGroups`، التي تقسم العمل إلى دفعات عند 90 عبارة. لذلك لا تكفي تسمية طلب جديد «ذريًا» مع إعادة استخدام مرحلة التنفيذ هذه كما هي.
- ينفذ `imgSync` أعمالًا بعد حفظ البيانات، وقد يصل إلى كنس R2. لا يدخل هذا المسار ضمن استعادة D1 الذرية المقترحة.
- تنتج `dsDomainStatements` عبارات الإحصائيات دون تنفيذها. وهي تحفظ فرق الغائب و`null` والصفر، والأقفال، وبيانات إسناد الإدخال.
- يورّث `mergeUsers` البصمات الغائبة بالمعرّف، ويحتفظ بحماية البصمة الحديثة من بعض نسخ البصمات القديمة. وتنتج `usersSessStmts` إبطال الجلسات المرتبط بحذف الحساب أو تجميده أو تغيير كلمته.
- سياسة الاستعادة الشاملة الحالية لمدير النظام فقط. في وضع الإنفاذ يلزم السبب المعتمد، وتبقى حراس الموارد والنطاق والثوابت فعالة. لن تُضاف صلاحية جديدة أو استثناء جديد لهذه العملية.

## عقد المسار المقترح

`POST /api/backup/restore`، بعد حارس المصدر والجلسة والحساب القائم، بمحتوى مقترح:

```json
{
  "uid": "معرف صاحب التبويب",
  "mode": "replace",
  "base": 123,
  "reason": "سبب الاستعادة",
  "data": {
    "bassam_depts_v1": "[...]",
    "bassam_auth_users_v1": "[...]"
  },
  "domains": {
    "dailyStats": {
      "version": 1,
      "data": { "haram": {}, "nabawi": {}, "locks": {} }
    }
  }
}
```

`base` مراجعة الحالة التي عُرضت للمستخدم قبل التأكيد، وليست مراجعة الملف القديم. يستخرج الخادم نسخ المفاتيح الحالية التي سيبني عليها الخطة، ويثبتها بحراس مقارنة داخل المعاملة. يجب كشف تغيّر الحساب أو التفويض أو الحالة أثناء الإعداد قبل قبول الخطة.

يرسل المتصفح الملف مرة واحدة بعد فك تشفيره محليًا. يبني الخادم `set` و`del` من العقد والحالة الحالية؛ ولا يقبل قائمة حذف حرة من العميل. تعاد سياسة الاستبدال الحالية صراحةً: البيانات التشغيلية للإدارات والمفاتيح العامة المعتمدة في النسخة، مع معالجة الحسابات المرتبطة بإدارات أزيلت وفق القاعدة الحالية. مفاتيح الجهاز والجلسة ليست بيانات خادم قابلة للاستعادة. أي عنصر تالف أو مجال أو إصدار غير مدعوم يرفض الطلب كله؛ لا يُتخطّى عنصر ثم يُعلن نجاح النسخة الكاملة.

النسخة الأولى تنفذ `replace` فقط. لا يُخترع معنى جديد لدمج الإحصائيات عند `mode=merge`؛ يرفض هذا النمط صراحة حتى يُحدد عقده ويُختبر. الاستعادة من شاشة الدخول دون جلسة تبقى مغلقة للمجال العلائقي، ولا تُستخدم لإنشاء صلاحية استعادة جديدة.

لا تُضاف حقول كلمات مرور إلى التصدير. إن احتاجت استعادة معينة تعديل اسم دخول صاحب الجلسة، تبقى مطالبة كلمة المرور الحالية وحارسها كما هما؛ لا يتحول وصف العملية بأنها استعادة إلى تجاوز لهما. كلمة المرور الحالية، إن استُخدمت في الطلب، لا تُحفظ في ملف أو سجل أو لقطة.

الردود المقترحة:

- `200`: إقرار المعاملة كاملة، مع المراجعة وعدد المفاتيح والصفوف ومرجع لقطة ما قبل العملية. لا إقرار قبل انتهاء `DB.batch`.
- `400`: جسم أو ملف أو إصدار أو نمط غير مدعوم، أو بيانات لا تحقق العقد.
- `401/403`: جلسة أو صلاحية أو نطاق أو سبب غير مقبول، باستخدام الحراس القائمة.
- `409`: تغير الجلسة أو المراجعة أو الحالة التي بنيت عليها الخطة؛ لا إعادة محاولة تكتب فوق الأحدث تلقائيًا.
- `413`: حجم الطلب أو الخطة خارج الحدود التي ثبت دعمها. لا تقسيم تلقائي إلى معاملات مستقلة.
- `500/503`: فشل المعاملة أو الخدمة؛ لا رسالة نجاح ولا تغيير متفائل لحالة المتصفح.

## إعداد الخطة دون تنفيذ جزئي

يضاف مسار إعداد داخلي موثوق إلى القلب الحالي، لا يفعله حقل من العميل. يعيد قرارات التقييم والصفوف المعتمدة التي ستكتب، بدل تخصيص مراجعة أو تنفيذ دفعات متفرقة. يستمر المرور عبر:

1. سياسة `backup.restore` والنطاق `full` وسبب العملية.
2. حراس المورد والنطاق ودمج الإسقاط وثوابت البيانات.
3. فحص تكرار المعرفات وأسماء الدخول ومفاتيح ربط الموظفين.
4. `mergeUsers` وحماية خفض البصمة وقواعد كلمة المرور الحالية والسياسة الأصلية.
5. حساب أحداث الأمن وإبطال الجلسات بالقواعد الحالية نفسها.
6. تحقق بنية الإحصائيات وإعداد عبارات الجداول العلائقية.

أي رفض أو تعارض، بما فيه رفض متأخر أثناء دمج الحسابات، يمنع تنفيذ جميع عبارات بيانات العملية. محاولات التحقق الأمني ومعدل الطلبات تبقى خاضعة لسياستها الحالية؛ لا تُستخدم كقناة لحفظ جزء من بيانات النسخة.

## تجميع SQL في معاملة واحدة

تُحوّل خطة الكتابة إلى صفوف معلومة البنية، ثم تنقل مجموعاتها بمعاملات JSON محدودة الحجم إلى `json_each`. هذه JSON وسيلة نقل للعبارات فقط؛ لا تُنشئ نسخة أعمال دائمة ثانية للإحصائيات.

| البيانات | التنفيذ المقترح داخل الدفعة |
| --- | --- |
| حراس المراجعات | حارس للمراجعة العامة وفحص قائمة نسخ المفاتيح عبر `json_each`، قبل تعديل الحالة |
| لقطة KV السابقة | `INSERT … SELECT` من صفوف KV الحالية إلى مخزن اللقطات القائم قبل حذفها؛ لا إعادة إرسال جميع قيمها كمعاملات |
| مفاتيح لم تكن موجودة | صفوف لقطة `existed=0` من قائمة المفاتيح، مع الحفاظ على عقد الاستعادة القائم |
| لقطة الإحصائيات | نسخة ما قبل العملية مرتبطة بلقطة الاستعادة وموسومة بإصدار المجال؛ لا تُعامل كمفتاح KV حي ولا يستعيدها مسار rollback قديم إلى KV |
| KV الجديد | حذف المفاتيح المتأثرة ثم إدخال صفوف `{k,seq,v}` على مجموعات بايتات محدودة؛ الحفاظ على ترتيب القطع |
| الإحصائيات | عبارات المجال المطبّع، مع ترتيب الأبناء والآباء المتوافق مع المفاتيح الأجنبية |
| المراجعات | إدخال/تحديث مجمع لصفوف `revs`، وتحديث `meta.rev` داخل المعاملة نفسها |
| التدقيق والأمن | إدخال مجمع للصفوف التي أنتجتها القواعد القائمة، دون كلمات مرور أو بصماتها ضمن أحداث التدقيق |
| الإنفاذ | إدخال مجمع لصفوف قرارات الصلاحية المقررة |
| الجلسات | حذف مجمع للجلسات التي حددتها سياسة الحسابات نفسها، مع الحفاظ على استثناء جلسة صاحب تغيير كلمته حيث ينطبق |

تظل اللقطة داخل الخادم، ويستمر تعقيم أي رد أو تصدير قد يغادره. لا يُعاد استخدام مسار rollback قديم إذا كان سيحول لقطة الإحصائيات إلى كتابة KV متقاعدة: إما أن يستخدم الخطة الذرية نفسها، أو يرفض قبل أي تغيير إلى أن يكتمل دعمه.

تُنشأ المراجعة الجديدة من الحالة المتحقق منها داخل الدفعة، بدل استدعاء `nextRev` ككتابة مستقلة في هذا المسار. ترتيب التنفيذ: الحراس، لقطة الحالة السابقة، تعديلات البيانات والجلسات، المراجعات وسجلات العملية. كل ذلك داخل استدعاء `DB.batch` واحد، دون `commitGroups` المتعدد أو `imgSync` بعده. أي إخفاق SQL متأخر يلغي العملية واللقطة والمراجعات والتدقيق المتعلق بنجاحها.

يجب قياس حدود D1 الفعلية للبيئة المقصودة قبل اعتماد عدد العبارات وأحجام المعاملات. تبقى قيمة تجزئة النقل الحالية للإحصائيات 500KB أساسًا محافظًا للاختبار، وليست إثباتًا لسعة كل عملية استعادة. التجزئة هنا داخل الدفعة الذرية نفسها، ولا تعني تعدد المعاملات.

## حد الجسم 8MB والحجم الفعلي

حد `/api/dstats` الحالي 8MiB، بينما بقية المسارات غير المخصصة لها حدود أصغر. لا يعني ذلك أن مسار الاستعادة المقترح يدعم نسخة Preview السابقة: حجم تصديرها المقارب 8.8MB ليس قياسًا لبايتات طلب JSON الجديد. إزالة البصمات ومفتاح الإحصائيات القديم، وإضافة أغلفة JSON وتهريب النصوص، قد تغير الحجم في الاتجاهين.

قبل تنفيذ العقد يجب قياس `UTF-8 byteLength(JSON.stringify(request))` للملف الفعلي المصرح به خارج Git، وإعلان حجم وحد الطلب دون تسجيل المحتوى. إذا تجاوزه الجسم فلا يجوز إعلان الوظيفة مكتملة مع النسخة الحقيقية. يحدد للمسار سقف منفصل مبرر بالقياس واختبار الذاكرة، أو يتخذ قرار عقد آخر صريح. لا تُفترض كفاية 8MiB ولا تُرفع الحدود عشوائيًا.

يفحص العميل الحجم قبل الإرسال، والخادم البايتات الفعلية قبل التحليل والخطة، مع وجود أو غياب `Content-Length`. تبقى مجموعات معاملات SQL أصغر من الجسم الكلي؛ وإلا نُقلت مشكلة الحد من HTTP إلى D1.

## الصور وR2

معاملة D1 لا تتضمن R2. لذلك لا يصح رفع أجسام صور على R2 في طلبات منفصلة ثم وصف العملية كلها بأنها ذرية. كما لا يجوز أن تنهي الاستعادة العمل باستدعاء كنس يحذف حاويات أو أجسام R2.

يمكن إدخال تعديل مراجع الصور وبيانات ملكيتها الموجودة في D1 في الدفعة نفسها إذا تحقق الخادم من وجود الأجسام المطلوبة وصلاحية ربطها وفق الحراس القائمة. يلزم إعداد عبارات فهارسها قبل التنفيذ؛ لا تشغيل `imgSync` المعتاد بعد الإقرار.

أما نسخة تحتوي أجسام صور جديدة أو تستلزم استبدال أجسام على R2، فتُرفض كاملة قبل أي كتابة إلى أن يوجد عقد واضح لهذا الحد واختبارات فشله. لا تُسقط صورها ثم تُعلن استعادة ناجحة. يجب فحص نسخة الحجم الفعلي لتحديد هل ينطبق هذا الحد عليها؛ لا يُستنتج غياب الصور من جرد KV وحده. لا حذف R2 ضمن هذه الخطة.

## الاختبارات الملزمة قبل رفع الحظر

1. استعادة فعلية ناجحة لـKV والإحصائيات والمراجعات والتدقيق ولقطة ما قبل العملية بإقرار واحد.
2. عطل محقون في أول ووسط وآخر عبارة: بقاء كل بيانات المجالات والمراجعات والجلسات وسجلات نجاح العملية كما كانت، دون لقطة نجاح جزئية.
3. كاتب متزامن على KV أو الإحصائيات، واستعادتان متزامنتان: إقرار واحد أو تعارض صريح، دون تحديث ضائع أو خلط نسختين.
4. رفض موظف ومدير إدارة للاستعادة الشاملة، وفحص السبب والنطاق والحساب المجمد وتغير الجلسة؛ دون توسيع `backup.restore`.
5. 13,006 حسابات صناعية ثم النسخة المحلية المصرح بها: مقارنة أعداد الحسابات والأدوار وارتباطات الإدارات، ومقارنة البصمات والسياسات وACL بايتًا ببايت أو ببصمات تحقق فقط، دون طباعة قيمها. يميز الاختبار بين ما استُعيد عمدًا من الملف وما يجب توريثه من الخادم.
6. بصمات غائبة أو قديمة، ومنع خفض البصمة، وكلمة مرور حالية خاطئة أو غير مدعومة، ومحاولة إزالة آخر مدير صالح، وتكرار المعرفات وأسماء الدخول. يبقى السلوك مطابقًا لحراس الحسابات الأصلية.
7. نسخة تعادل الحجم المعروف: 154 مفتاحًا و159 صف KV على الأقل، مع القطع الطويلة ونصوص متعددة الأسطر وUTF-8. إثبات تنفيذ دفعة واحدة فعلًا، وعدم تطبيق حد90 الذي يرفض الحالة المعروفة.
8. حد الجسم وحجم المعاملات وعدد العبارات والذاكرة، مع الجسم المقطع و`Content-Length`؛ ورفض كامل عند تجاوز أي حد.
9. صور موجودة ومفقودة وأجسام جديدة وفشل التحقق: تطابق فهارس D1 أو الرفض الكامل، وعدم أي كتابة أو حذف R2.
10. فشل الشبكة أو الرفض أو استجابة ناقصة أو إقرار بمراجعة أقدم: الاحتفاظ بالملف والتأكيد والمسودة، وعدم التوست الناجح أو إعادة التحميل قبل الإقرار الحقيقي.
11. استدعاء واحد من الواجهة للاستعادة، دون حفظ KV أو حسابات أو صلاحيات أو dstats عبر `localStorage` أو طلبات حفظ متتابعة.

## الملفات المتوقعة للتنفيذ اللاحق

- `workers/parts/054-image-contract.js`: فصل إعداد نتائج التقييم عن تنفيذها في مسار الاستعادة، مع الإبقاء على المسار العادي وحراس الحسابات والموارد.
- `workers/parts/020-dstats.js`: إعادة استخدام التحقق والترميز والعبارات دون استدعاء commit مستقل.
- `workers/parts/051-audit-diff.js` و`062-enf-save.js` عند الحاجة: استخراج بيانات صفوف الأحداث والجلسات واللقطات لتجميعها دون تكرار قواعدها أو تغييرها.
- `workers/parts/063-enf-api-and-handler.js` و`055-sec-headers.js`: المسار والجلسة والحد المبرر للحجم.
- `src/api/contracts.json` و`src/schemas/api/bodies.schema.json`: عقد الطلب والرد والشكل، ثم التوليد من المصدر.
- `src/modules/admin/logic.js` وخدمة العميل المناسبة: إرسال واحد وانتظار الإقرار، مع إبقاء الرفض الواضح للحالات غير المدعومة.
- اختبارات المجال والعقود والاستعادة والواجهة والأمان، ثم إعادة توليد العامل والحزمة. لا تحرير للمخرجات المولدة يدويًا.

لا يبدأ التنفيذ تحت مجموعة اختبارات جارية على الملفات نفسها. ولا تعتبر الخطة جاهزية للنشر أو تصريحًا بلمس Production. معيار رفع الحظر هو نجاح المعاملة الواحدة على الحجم الحقيقي وجميع اختبارات الفشل المذكورة، مع حدود صور وحجم معلنة بوضوح.
